It’s 2020 but I still see questions everywhere about _“Which state management solutions should I use?”_ in [React](React).

- Should I use [Redux]? Oh, [I might not need it][noredux]?
- What then? Is [local state][ls] enough or do I need [React Context][ctx]?
- How about [MobX] ([mobx-state-tree]?), [Recoil], [Storeon], [Zustand]?
- Or should I embrace streams/observable and use [RxJS]?
- If my backend is GraphQL, should I use dedicated clients like [Apollo Client][apl] or the ones above would be enough?
- There’s also a new trend on [“data-fetching libraries” which is higher-level than state-management libraries][df] but still backend agnostic. Or should I just use [React Query][rq] or [SWR][swr]?

## Why do I recommend this?

I have observed that a single piece of data will be reused in multiple views. Let’s consider a chat application where you can mark certain chats as pinned.

![](https://static.dt.in.th/uploads/2020/11/04/why-abstract-state-1.svg)

Before [React Query][rq] existed, I might use [Redux] to do this. So naturally, each view component would use [useSelector] and [useDispatch].

[useselector]: https://react-redux.js.org/api/hooks#useselector 'Hooks | React Redux'
[usedispatch]: https://react-redux.js.org/api/hooks#usedispatch 'Hooks | React Redux'

![](https://static.dt.in.th/uploads/2020/11/04/why-abstract-state-2.svg)

Fast forward to 2020, and now [React Query][rq] is a thing. Now I am envy of all the greenfield apps that gets to use it.

Looking back, the original implementation we have its full of boilerplate and is bug-ridden. Sometimes the state would not synchronize correctly due to me forgetting to put `useEffect` in some places. The buggy code is then copy-and-pasted all over the place.

And so, it seems more effective to just switch to React Query. In this case I would use the [useQuery] and [useMutation] hooks instead. But then I would need to change several components. This is a laborious and boring task.

[usequery]: https://react-query.tanstack.com/docs/guides/queries 'Guides & Concepts: Queries | React Query | TanStack'
[usemutation]: https://react-query.tanstack.com/docs/guides/mutations 'Guides & Concepts: Mutations | React Query | TanStack'

### In an alternative universe…

Now, what if, back at that time, I decided that _“UI components should not be aware of what state management solution is being used”_?

Then after the initial implementation using Redux, I would spend a few minutes [harvesting][harvest] the data-binding code and refactor it into a custom hook.

![](https://static.dt.in.th/uploads/2020/11/04/why-abstract-state-4.svg)

## Decoupling UI from state management

Multiple techniques exist:

- [**Hooks**][hooks] are generally the cleanest solution

  ```js
  const pinnedChats = usePinnedChats()
  ```

- **Connector components** (using [render props][rp]) can help if you have a lot of class-based components. Class components cannot use hooks so in these cases you can create an adapter which lets class components access hooks through render props.

  ```js
  function PinnedChatsConnector({ children }) {
    const pinnedChats = usePinnedChats()
    return children({ pinnedChats })
  }
  ```

- [**Higher-order components**][hoc] are generally considered legacy. If your code have a lot of higher-order components and you are not ready to rewrite the whole component yet, you can, again, create an adaptor that allows connectors to be used as a HOC.

  ```js
  function withPinnedChats(WrappedComponent) {
    return Object.assign(function WithPinnedChats(props) {
      return (
        <PinnedChatsConnector>
          {({ pinnedChats }) => (
            <WrappedComponent {...props} pinnedChats={pinnedChats} />
          )}
        </PinnedChatsConnector>
      )
    })
  }
  ```

In 2018, I talked about this idea with more examples in my talk [Smells in React Apps][smells].
